# Adding companies and problems

Every problem is a folder. The app discovers it automatically; there is no registry to edit.

```
problems/
  <company-slug>/
    company.json            # name, tagline, notes, sources
    <problem-slug>/
      problem.md            # frontmatter + description (Markdown)
      starter.py            # what the candidate sees first
      solution.py           # reference solution (used to generate expected outputs)
      tests.py              # test INPUTS (+ optional scale() for the Complexity view)
```

## company.json
```json
{
  "name": "Acme AI",
  "tagline": "One line on what the company does and what their loop looks like.",
  "notes": "What gets asked most, what interviewers care about.",
  "sources": [{"title": "Where this came from", "url": "https://..."}]
}
```

## problem.md
```markdown
---
title: Rate Limiter
difficulty: Medium            # Easy | Medium | Hard
source: Acme AI phone screen (reported 2025)
order: 1                      # sort order within the company
minutes: 45                   # suggested interview length (sets the countdown)
timeout: 20                   # seconds for a whole test run (default 20)
tags: design, sliding window
---
Problem statement in Markdown. State the exact function/class signature in a code block,
give at least one worked example, list constraints, and spell out any ambiguous rules
(ties, edge cases, what to return when empty). Multi-part questions: use "### Part 1",
"### Follow-up" headings and tag the tests the same way.
```

### Reported vs. practice problems
If the question was actually reported by candidates, say where in `source:` (e.g. `Acme AI phone screen (reported 2025)`).
If you couldn't find the actual question and wrote one in the company's reported style, the `source:` line **must start
with "In the style of"** (or "Loosely based on"), e.g. `In the style of Cognition's practical rounds. Not a reported question.`
The UI labels these as "Practice · in their style" automatically.

## starter.py
Signatures only, with `pass` bodies. Keep every function/class the tests call.

## solution.py
A clean, idiomatic reference solution with a short docstring giving its time/space complexity.
**Expected outputs are generated by running this file**, so it must be correct and deterministic.

## tests.py
```python
import random
from engine.spec import fn, cls

def tests():
    rng = random.Random(1)          # always seed randomness

        fn("Big random", "my_func", big_list, 7, hidden=True),            # hidden: only on Submit
        cls("Follow-up case", "MyClass", [10], ops, tag="Follow-up"),
    ]

def scale(n):                       # optional, enables the Complexity button
    return fn(f"n={n}", "my_func", list(range(n)), n)

SCALE = {"sizes": [1000, 2000, 4000, 8000, 16000, 32000], "label": "n = len(nums)", "per_op": False}
```
Options: `tag=` ("Part 1" default, "Follow-up", "Part 2", "Stretch" = Submit-only), `hidden=True`,
`float=True` (1e-6 tolerance), `compare="unordered"` (list order doesn't matter),
`expected=` (supply the answer yourself for very slow cases).

Arguments and return values must be JSON-compatible (lists, dicts with string keys, numbers, strings, bools, None).
Tuples come back as lists and sets as sorted lists.

## Validate
```bash
python3 tools/validate.py <company>             # or <company>/<problem>, or nothing for all
```
It generates expected outputs, checks the reference passes, the starter compiles and the benchmark runs.

## Quality bar
- Write problems in your own words. Don't paste paywalled content.
- Cite where the question was reported in `source:` and `company.json`.
- 6+ visible-or-hidden tests per problem covering edge cases, plus at least one larger hidden test.
- Follow-ups as separate tagged tests, so people can pass Part 1 first.
